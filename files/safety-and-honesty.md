# Safety and Honesty

This is a judging criterion, not a footer. Treat every rule here as a build requirement with a test
behind it.

## 1. The two disclosures (exact strings)

Rendered by `<DisclosureStrip />` in the root layout, on every route, never dismissible:

> **Independent prototype — not an official government service.**

And on `/`, `/about`, `/demo`, and any screen showing a government-shaped record:

> **Synthetic demo data. No live government, banking, Aadhaar, PFMS or NPCI system is connected.**

`tests/unit/content.spec.ts` asserts both strings exist and that the strip is in the root layout.

## 2. Claims the product must never make

Enforced by the artifact post-validator (`ai.md` §6) and the content scan (`testing.md` §4):

| Never | Because |
|-------|---------|
| "We checked PFMS / NPCI / Aadhaar / your bank" | We checked nothing. We read what the student told us. |
| "Your application is with Officer X / at desk Y" | We cannot see inside any office. Claiming so is the exact dishonesty the research warned against. |
| "Your money will be credited on <date>" | We cannot know. No date promises, ever. |
| "We have submitted your grievance / filed your RTI" | The student sends everything themselves. |
| "Officially verified" / any government emblem, seal or logo | We are not official and must not look it. |
| A specific national statistic about scholarship payment failures | No such verified figure exists in our sources. Say that instead. |
| "This is definitely why" at band `MEDIUM` or `LOW` | Confidence language is bound to the band, in code. |

## 3. Provenance is a type, not a habit

```ts
type Provenance = 'PUBLIC_RULE' | 'SIMULATED' | 'USER_STATED' | 'AI_INFERENCE';

// Every fact-bearing component requires it:
type FactRowProps = { label: string; value: string; provenance: Provenance; note?: string };
```

There is no default value and no optional marker. A component that renders a value without a provenance
will not typecheck. `tests/e2e/provenance.spec.ts` counts rendered fact rows against rendered badges on
every route and fails on a mismatch.

Badge meanings shown to the user (`ui-ux.md` §4.2):
`Public rule` · `Demo record` · `You told us` · `Our estimate`.

## 4. Uncertainty rules

- Confidence language is generated from the band, never chosen by the model:
  `HIGH` → "Fairly confident" · `MEDIUM` → "Possible" · `LOW` → "Not enough information yet".
- The **"What we don't know"** block is mandatory and can never render empty. If the engine produces no
  unknowns, the UI renders the single highest-value remaining check instead.
- At band `LOW` no rail stage may be `BLOCKED`, and the action plan must be an information-gathering step,
  not a fix.
- Every hypothesis carries `disproveBy` and it is shown. Telling the student what would prove us wrong is
  a feature, not a hedge.

## 5. Data handling

**We do not want the student's personal data and we build so we cannot keep it.**

- `lib/redact.ts` runs on **every** text write path — free text, pasted status, screenshot-extracted text,
  answers, notes, artifact edits. Patterns removed and replaced with `[removed]`:
  - 12-digit sequences with optional spaces/hyphens (Aadhaar-shaped)
  - 9–18-digit sequences (account-shaped)
  - "OTP" adjacent 4–6-digit sequences
  - PAN-shaped `[A-Z]{5}[0-9]{4}[A-Z]`
  A 10-digit phone number is **not** blocked (the student may need it in a letter placeholder) but is
  never required and never pre-filled.
- Uploaded images are held in memory only, never written to disk, object storage, logs or the database.
  There is no file storage in this application.
- No cookies, no analytics, no third-party scripts, no trackers.
- Case tokens are unguessable but not secret; the UI says so plainly: *"Anyone with this link can see this
  case. Don't share it."*
- 7-day retention, swept lazily, stated on `/about`.
- Logs record lengths and durations, never content.

## 6. Scope honesty on `/about` (write it, don't imply it)

Four sections, in the product's own voice:

**What is real.** The failure states, the escalation ladder and the "how to check" steps are drawn from
publicly documented scheme and banking processes. The reasoning about which failure you are in is ours.

**What is simulated.** Every application, payment, routing and bank record in this prototype is
fictional and generated by us. Verification reads our own synthetic records. The credit shown at the end
of a demo case is not a real payment.

**What is inferred.** Facts marked *Our estimate* were worked out by a language model from what you wrote
or from a screenshot. They can be wrong. You can edit any of them.

**What we don't know.** There is no verified national statistic for how many scholarship payments fail at
the Aadhaar-seeding or payment-routing stage. Our understanding rests on state audit findings and state
notifications, which are real but local. Our probability weights are product judgement, not measured
frequencies. We say this because a tool that guesses about your money should be clear about what it is
guessing with.

## 7. Wellbeing and tone

Students reach this tool under fee-deadline pressure. Therefore:

- Never blame the student. The copy assumes the system failed, because usually it did.
- Never imply the money is lost. Say what is known and what the next step is.
- Where a fee deadline is flagged, the action plan surfaces the interim step (talk to the college about a
  deadline extension while the payment is chased) as a first-class action, not an afterthought.
- No countdown timers, no urgency banners, no scarcity language.
- If a student says something distressing in the free-text box, the product does not analyse it, store an
  interpretation of it, or respond to it — the redaction and extraction pipeline only pulls the closed set
  of facts in `database.md` §4, and everything else is left alone.

## 8. Attribution and IP

- Original design only. No government emblem, seal, logo, colour scheme, portal layout or copy is
  reproduced. We studied how the journey works; we copied nothing.
- No government code, infrastructure or private system is copied or reverse-engineered.
- Fonts are open-licensed (Bricolage Grotesque, IBM Plex — both OFL). Record the licences in
  `docs/licences.md` at build time.
- All demo names are fictional and suffixed `(demo)`.

## 9. The honest answer to the hardest judge question

> *"Portals already have status trackers and helpdesks. Why does a student need this?"*

Because the portal does not hold the failing fact. Sanction status is set when a sanction is issued, not
when money lands, and the failure — if there is one — lives in a payment system, a routing layer or a bank
that the student cannot see and the portal does not report on. A state audit found lakhs of scholarship
beneficiary accounts not Aadhaar-seeded, with a dedicated finding on failed transactions, and state
notifications record students rejected specifically under DBT-enablement errors. From where the student
stands, all of those look identical: "approved, no money."

This product does not claim to see into those systems. It does the thing nobody currently does for the
student: it separates the possibilities, says honestly which one it cannot rule out, tells them the one
check that would settle it, and hands them the letter to take to the counter on Monday.

That is also the limit, and we say it on screen: we diagnose and draft. We do not move money, and we
never pretend to.
